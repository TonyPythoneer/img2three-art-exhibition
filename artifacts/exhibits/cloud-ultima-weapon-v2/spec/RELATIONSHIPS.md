# RELATIONSHIPS — what feeds what

`CURRENT-MODEL.md` says _what the model is_. This says _how the files hang together_: which one
is upstream of which, what regenerates what, and which relationships are load-bearing enough
that breaking one silently corrupts a later step.

Read this before changing anything outside the model factory.

---

## 1. The exhibit's place in the repo

```
src/exhibits/index.ts            ← the ONLY registry. Adding an exhibit here is what creates:
   │                                 · the SSG route (vite.config.ts reads this file)
   │                                 · the entry-site gallery card (ExhibitGrid.vue)
   │                                 · the doc links on the exhibit page
   ├─→ vite.config.ts  ssgOptions.includedRoutes  →  dist/cloud-ultima-weapon-v2/index.html
   ├─→ src/components/home/ExhibitGrid.vue        →  the gallery card + its cover image
   └─→ src/pages/[slug].vue  STAGES map           →  UltimaV2Stage.vue

src/components/home/heroStage.ts  heroEntries()   →  the landing-page turntable
```

**Four connection points, and missing any one leaves the exhibit invisible or broken:**

| Point                                                       | Miss it and…                                                                                                                                                                  |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `exhibits/index.ts` entry                                   | no route, no card, nothing                                                                                                                                                    |
| `[slug].vue` `STAGES` map                                   | the route renders a plain document page with no viewer                                                                                                                        |
| `heroStage.ts` `heroEntries()`                              | the landing turntable skips it and hovering its card does nothing                                                                                                             |
| root-level `*.png` + `prompt.txt` **in the exhibit folder** | no cover image, no prompt text — the globs are `exhibits/*/*.png` and `exhibits/*/*.txt`, **direct children only**. Images in `assets/` or `references/` are never picked up. |

## 2. The four Ultima Weapon reconstructions

They are **not** four versions of one thing. Two independent readings of the same weapon, from
two different references:

```
146×292 game render                    210×434 artwork crop + component contract
(reference-ultima-weapon.png)          (reference-artwork-crop.png)
        │                                       │
        │  reads SIX spokes, 47 nodes           │  reads FOUR drivers, 19 parts
        ▼                                       ▼
/cloud-ultima-weapon (removed)          /cloud-ultima-weapon-v2
  three agents, same reference          one model
                                         (this exhibit)
```

The three tabs on the old `/cloud-ultima-weapon` exhibit **were** comparable to each other — same reference,
same brief, three agents. V2 is not comparable to them and was deliberately built as a separate
exhibit (the old v1 exhibit has been removed). Do not "fix" one exhibit's part count using the
other's numbers.

### The order is not optional

`author_spec.py` clears `reviewHistory` on every run, on purpose — a review scored a component
tree that may no longer exist. So the sequence is always:

```
python3 spec/author_spec.py            # 1. spec, reviews cleared
<capture renders>                      # 2. artifacts
zsh spec/run_gates.sh                  # 3. gates read the artifacts
zsh spec/record_reviews.sh             # 4. reviews written back (run 3× — passes unlock in order)
```

Running `record_reviews.sh` before `author_spec.py` writes reviews that the next author run
deletes. Running gates before capturing renders reads stale PNGs and reports numbers for a model
that no longer exists — which is exactly how a defect survived one acceptance review.

**And since 2026-08-10 the manifest is an INPUT to step 1 as well as an output of step 2**, so a
geometry change needs two turns of that crank:

```
<capture>  →  author_spec.py  →  <capture>  →  run_gates.sh  →  record_reviews.sh
```

`author_spec.py` reads every component's `dimensions` and `transform.position` out of
`artifacts/ultima-v2/full/parts.json` rather than carrying a second hand-typed copy of each box,
and `audit_records.py` re-checks the spec against the same manifest — so authoring against a
STALE capture fails the gate loudly instead of shipping a spec that describes a model nobody
built. That is what the two hand-typed copies had already done, eight times over: see §5's box row.
When geometry has not moved — the common case, e.g. a documentation pass — one turn is enough,
because the manifest step 1 reads is the one step 2 would produce.

## 4. Which documents cite which numbers

**A document citing another document is how drift starts.** The per-part ΔE once existed as three
different values at once across two reports. `spec/audit_records.py` now enforces the rule and
`run_gates.sh` runs it: re-derive from `parts.json` and the gate JSON, never from a report. Its
docstring is the specification; two things it learned the hard way are worth knowing before you
write a number down.

- It scans every `.md` under the exhibit. It used to scan `index.ts`'s v2 block as well, because
  the exhibit card carried a `decisions[]` array of build-log prose that quoted two retired driver
  roots for a whole correction pass while every `.md` in the folder was clean. That array has since
  been removed from the registry — the card no longer carries prose, only doc links, whose targets
  are still checked. **Put narrative back on the exhibit record and it has to come back into this
  net**, or the same drift returns with nothing watching for it.
- A table row is only excused from the retired-figure check if it _looks_ like a before/after
  table. A blanket "starts with `|`" exemption is how `confidence-report.md`'s final-numbers table
  kept quoting a dead IoU through two passes.

## 6. What is deliberately NOT wired up

- **`spec/generated/blockout-factory.ts.txt`** — the forge generator's output. Kept as evidence
  that the generation step ran; the shipped model is hand-authored. It is `.txt` so `vue-tsc`
  does not typecheck it.
- **`spec/pbr-evidence/*/`** — extraction ran on five verified crops and its scalars were
  rejected. Nothing in the model reads these. See that folder's README for why.
- **`tools/capture.mjs`** vs **`tools/capture_ultima.mjs`** — the second is the one this exhibit
  uses, via `--route ultima-v2-harness`. It is shared with the Fable and Opus runs; the
  `VIEW_SIZE` table has entries for all of them.
- **`src/pages/ultima-v2-harness.vue`** is intentionally absent from
  `ssgOptions.includedRoutes` — it mounts WebGL, and prerendering would evaluate three.js in
  node where there is no GL context.

**One rule for evidence pictures, and it is the opposite of "keep everything":** every PNG under
`spec/zoom-*/` must either be re-produced by a script in `spec/` or be cited by a document. A
picture that is neither cannot be checked against the current model and cannot be reasoned from —
it is a claim about a build nobody can identify. Fourteen were deleted from `spec/zoom-guard/` on
2026-08-10 under that rule, having survived the jaw's four-point outline, the grip's tang and
`guardCore`. What is left is produced by `zoom_sketch_guard.py` (six sketch reads plus the
side-by-side) and `measure_guard_joints.py` (five crop reads plus two artwork-vs-render pairs), so
re-running those two rebuilds the whole folder against the model as it stands.

`verify_v2_route.mjs` is the end-to-end one: it checks the entry-site card exists, that clicking
it navigates to the route, that the viewer mounts, that the part inspector lists its parts, and
that every control drives the viewer without a console error — the seven panel chips, the
black-box intensity slider (which only exists in that mode), and the inspector's isolate and
hide/show buttons, each as a ROUND TRIP so that un-isolating is checked as well as isolating.
A model that builds but whose controls throw is not shipped.

**Its label list is a copy of `UltimaV2Stage.vue`'s template and it has gone stale once already.**
It named six family chips — 外殼 / 能量核心 / 背脊 / 護手 / 握把 / 全部 — that were removed when
isolation moved into the shared part inspector, so every run timed out on a button that no longer
existed. A red end-to-end check that is red for a stale reason is worse than no check: it gets
ignored, and then it cannot report a real one. Change the panel, change this list in the same edit.
