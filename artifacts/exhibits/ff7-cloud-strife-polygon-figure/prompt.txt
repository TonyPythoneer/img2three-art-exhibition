0.1 The img2threejs skill is the runtime authority.

    `ART/.img2threejs/state.json` ALREADY EXISTS from an earlier attempt, and
    `forge/state.py init` refuses to overwrite an existing state file (it prints
    `state error: refusing to overwrite existing state` and exits 2). This is a
    full-overwrite rebuild, so delete it first, together with the stale spec:

      mv ART/.img2threejs/state.json ART/.img2threejs/state.json.bak

    Move, do not delete. The old state's `reviewHistory` is the only record of the
    previous attempt and costs nothing to keep. Do not read the .bak files for

    Then, before anything else:

      python3 forge/state.py init --state ART/.img2threejs/state.json \
        --reference REFS/front.webp --profile character \
        --spec ART/spec/object-sculpt-spec.json \
        --max-per-pass 3 --max-total 60
      (ART / REFS name the directories in §0.0; expand them to absolute paths on
       the real command line — they are not literal strings to paste)

    At every start, resume, and correction loop, before touching code:

      python3 forge/next.py --state ART/.img2threejs/state.json [ART/spec/object-sculpt-spec.json]

    OMIT the positional spec argument until `ART/spec/object-sculpt-spec.json`
    exists on disk. next.py reads that file directly and exits 2 if it is missing
    or unparseable; with no positional argument it reports the pre-spec checklist
    instead. Once the spec exists, always pass it.

    Exit codes: 3 (or `status=stopped`) is a HARD STOP — report and request input.
    2 is a script/state/invocation error — fix the command or the paths; it says
    nothing about the model, and it is never a reason to correct geometry.
    Never reconstruct progress from chat memory.

    Wherever this document says `--pass-id <pass>`, `<pass>` is the pass id that
    `forge/next.py` prints as `current pass` for the current spec. Do not invent one.

    corrected three times and is still wrong, the READING is wrong, not the code —

§1 COORDINATES AND CONVENTIONS
═══════════════════════════════════════════════

1.1 Y up, ground at Y=0, total height (hair tip to sole bottom) normalized to
    1.000, Z forward (the figure faces +Z). Right-handed, as Three.js is.
    Every tolerance written `< 1e-6` or `± tol` in this document is in these
    normalized units, where 1.000 is the whole figure.

1.2 LEFT and RIGHT always mean the FIGURE'S OWN left and right.
    front.webp: figure's right = image left. back.webp: figure's right = image right.
    left.webp = the figure's LEFT side faces the camera.
    right.webp = the figure's RIGHT side faces the camera.

    In model space this fixes the sign: facing +Z with +Y up in a right-handed
    frame, the figure's LEFT is +X and the figure's RIGHT is -X. Every sided
    factory takes `side: "L" | "R"` and derives `sideSign = side === "L" ? 1 : -1`.
    Nothing else in the codebase may hardcode that sign.

1.3 Handedness, verified under zoom. Do not get this backwards:
    BLACK PAULDRON + GREY BRACER = the figure's LEFT.
    The figure's RIGHT is a bare deltoid, no bracer, black glove only.

1.4 THE POSE IS BAKED INTO THE PARTS. This is a fixed-pose toy; there is no
    animation requirement. Author every part in the pose the references already
    show — forward-broken elbows, upper arms abducted and leaned forward, feet
    splayed outward. Each part's local origin is its own UPPER socket AS POSED,
    so the local origin is the zero vector in the part's own frame.
    => Stage 1B assembly is pure translation. No rotations there.

1.5 MIRROR REUSE. Stage 1 carries no colour and no material, so every left/right
    pair is geometrically IDENTICAL up to a mirror. One factory emits one
    geometry, parameterised by `sideSign` (§1.2). Do not author two versions and
    do not copy-paste.

      Pure mirror pairs (8): sole / ankle / calf / knee / thigh /
                             upperDeltoid / lowerDeltoid / backArm
      Not a pure mirror (1): frontArm — the figure's LEFT wrist segment has width
                             factor ~1.05, the RIGHT has 1.0. One parameter apart,
                             but both sides still need looking at.
      Self-symmetric singles (5): pelvis / chest / waist / neck / head

    This classification is MEASURED, not assumed. Band-by-band mirror check on
    front.webp's silhouette (prior measurement — §0.6 applies):
      upper arms       mirrorIoU 0.943  extent diff  1px  -> pure mirror, best score
      boots + soles    mirrorIoU 0.914  extent diff  1px  -> pure mirror
      pant legs        mirrorIoU 0.958  extent diff  3px  -> pure mirror
      pelvis           mirrorIoU 0.933                    -> self-symmetric
      shoulders        mirrorIoU 0.915  extent diff  2px  -> pure mirror
      forearms + hands mirrorIoU 0.875  extent diff 11px  -> NOT a pure mirror
                                                             (the wider bracer)
      head + hair      mirrorIoU 0.657                    -> STRONGLY asymmetric
                                                             (the spikes; expected)

    ⚠ MIRROR ABOUT THE BEST-FIT AXIS, swept in half-pixel steps to maximise
      whole-figure IoU (docs/agents/claude.md, "Banded mirror IoU") — NOT about
      the bounding-box centre. Re-derived on front.webp: bbox centre scores 0.825,
      best-fit axis 0.858. The prior measurement's whole-figure figure of 0.858
      is that same best-fit number, so the table above is on the right axis; a
      bbox-centre sweep would drag every band down with it.

    ⚠ READ THAT TABLE BY THE EXTENT DIFFERENCE, NOT BY THE IoU. The whole-figure
      score (0.858) is the noise floor from photographic perspective and staging,
      so 0.875 for the forearms is NOT below the floor and on IoU alone would look
      like a mirror. What separates the forearms from every pure pair is the
      lateral extent difference: 1-3px on the pure pairs, 11px here. The IoU
      column only corroborates.

    ⚠ What this saves is REVIEW TURNS, not just lines of code: for a pure mirror
      pair, render and compare ONE side against the reference; the other side is
      covered by the mirror-consistency assertion in §5.10, with no second visual
      review.

    ⚠ Instantiate exactly ONE material for the whole of Stage 1 and share it
      across every part. A `new` per part is waste, and it makes a later material
      change a 23-file edit.

1.6 THE OBJECT-TREE NAMING IS THE PART TABLE. src/utils/partInspector.ts reads the
    object graph, not a registry. Its exact rules, which the naming in §2 must
    satisfy:
      - a NAMED Mesh is always a part.
      - a NAMED Group is a part only if it contains at least one mesh AND contains
        no selectable descendant. A named Group that contains another named,
        mesh-bearing node is a CONTAINER and is descended through instead.
      - a part's "group"/module is its nearest NAMED ancestor below the root; the
        root's own name is never reported as a module.
      - `kind` is `detail` only when the node is not itself a mesh and EVERY mesh
        under it carries `userData.explodeWithParent === true`. The flag is read
        on the MESH, not on the wrapping Group — setting it on the Group alone
        does nothing.
    Therefore sub-segments inside a factory (the forearm's three blocks, etc.)
    must stay UNNAMED. One factory = one part.

§3 STAGE 0 — MEASUREMENT AND TOOLING (the whole first turn)

Four deliverables (3.1-3.4). Missing any one of them means the user can see nothing.

3.1 spec/measure_landmarks.py -> spec/landmarks.json

    Silhouette extraction: corner flood fill, tol=18. Verified clean on all five
    references, including the armpit holes, the crotch notch, and the sole-slab
    ledge. Do NOT use a global threshold; it fails on all five.

    ⚠ THE FIGURE TEST NEEDS BOTH CONDITIONS. Flood fill only enters from the
      border, so white regions ENCLOSED by the figure get misclassified as figure:
        figure = (unreachable by flood fill from the border) AND (255 - min(r,g,b) > tol)
      Either condition alone is wrong. The enclosed regions are largest in
      more-angle (the gap between the legs) but exist in front / left / right too;
      measure and record the enclosed-pixel count for every view.

    ⚠ THREE CROPPING DEFECTS. The script must handle them; they are not noise to
      be ignored. The numbers below were re-derived with the exact rule above at
      tol=18 — reproduce them, and report any disagreement (§0.6).

──── SOCKET LEDGER (one name per mating point; both parts must use it) ────

Every part's local origin is its own upper socket (§1.4), i.e. the zero vector in
its own frame. Every OTHER named point it needs is emitted in `userData.sockets`.
A mating point has exactly ONE name, shared by the two parts that meet there —
that is what makes §5.5 checkable.

  part           origin (local zero)   emits
  ─────────────────────────────────────────────────────────────────
  sole           soleTop               —              (bottom face on Y=0)
  ankle          ankleTop              soleTop
  calf           calfTop               ankleTop
  knee           kneeTop               calfTop
  thigh          hip                   kneeTop
  pelvis         pelvisTop             hipL, hipR
  waist          waistTop              pelvisTop
  chest          chestTop              waistTop, neckBase, shoulderL, shoulderR
  upperDeltoid   shoulder              deltoidWaist
  lowerDeltoid   deltoidWaist          backArmTop
  backArm        backArmTop            elbow
  frontArm       elbow                 fist
  neck           neckTop               neckBase
  head           skullTop              neckTop

  - A sided emitter carries the L/R suffix (`hipL` mates with thighL's `hip`;
    `shoulderR` mates with upperDeltoidR's `shoulder`). Unsided names mate directly.
  - `chestTop` and `skullTop` are origins with no emitter: chest is the trunk
    anchor, placed in Stage 1B straight from the shoulder-line landmark, and head
    hangs off `neckTop`. `fist` is emitted and never consumed (terminal).
  - `neckBase` and `neckTop` are the two UPWARD mates: the part above sits on the
    part below, so both sides emit the same name and §5.5 compares them directly.

Build order (simple to hard, sockets chaining bottom-up):
  sole -> ankle -> calf -> knee -> thigh -> pelvis -> waist -> chest ->
  lowerDeltoid -> upperDeltoid -> backArm -> frontArm -> neck -> head

sole is first on purpose: it is the simplest, so it proves the gate machinery
runs before anything hard depends on it. Otherwise every later part is debugging
the tooling instead of the model. head is last because the hairline is locked last.


──── LOWER BODY: THESE ARE BLOOMER PANTS, NOT FITTED TROUSERS ────

pelvis / thigh / knee / calf are four segments of ONE pair of baggy pants, not
"a leg". The pants balloon to maximum at the hip, taper continuously downward,
gather at the pant-leg crease, and finish as a straight tube into the boot cuff.
So: thigh is NOT the widest point (pelvis is), and knee is NOT the anatomical
knee (the knee is covered by fabric and never visible).

Both the profile and front views show the gather line: the outer silhouette runs
as a straight TAPER, then hits a HARD CORNER at a specific height, then turns
near-vertical below it. That corner is a real line in the reference, not a
modeller's arbitrary cut.

§9 STAGE 5 — FULL INTEGRATION AND REFINEMENT (Stage 3 complete AND the user
   has said go)
═══════════════════════════════════════════════

This stage receives the assembled, coloured model and fixes what only assembly can
reveal. It ADDS NOTHING.

9.1 Scope. Permitted work, and nothing else:
    - close visible gaps and interpenetrations at joints
    - remove z-fighting between coplanar faces of adjacent parts
    - correct socket positions in the integration file
    - correct a part's shape BY EDITING ITS PART FILE (never the integration file)
    Forbidden here: new parts, new shape codes, new colour codes, new material
    codes. Anything that would add one of those re-enters at the stage that owns
    it and needs a fresh user order.

9.2 Method. Walk the joints in the order the sockets chain (§4's socket ledger),
    one joint per turn, each inspected at >=6x NEAREST against the matching
    reference crop. §0.3's one-item-per-turn cadence applies to joints here exactly
    as it applies to parts in Stage 1.

9.3 Gates:
    a. Four-view silhouette IoU, masked per §6, must EXCEED the Stage 1B result by
       more than measurementUncertainty. Equal is not passing — this stage exists
       to improve it.
    b. Every identity feature in §5.8 re-confirmed at >=6x on the assembled model.
       They were verified per part; assembly can break them.
    c. Total triangle count within the model budget recorded in the spec.
    d. §5.4's facet assertion re-run on the assembled model. Joint repair is where
       smoothing accidentally creeps in.

     - the user names one change

§11 GUESS LIST (deliver in the first reply; these five are already known)
═══════════════════════════════════════════════

1. FOREHEAD HAIRLINE POSITION. Completely hidden by the fringe; unmeasurable.
   Reading A: inset from the side-view hair-cap thickness — the hairline sits
     roughly one hair thickness above the brow
   Reading B: the hair-cap front edge cuts straight to the brow line
   Default A. The "skull + hairCap = back.webp outline" condition (§7.6) brackets it.

2. TRIANGULAR-PRISM COUNT FOR THE LEFT SIDEBURNS. The user wrote "two spikes ...
   appears to use two prisms".
   Reading A: 1 prism each, 2 total (consistent with the right sideburn)
   Reading B: 2 prisms each, 4 total
   Default A. §7.4's table and its 13-prism total assume A.

3. HEIGHT OF THE knee SEGMENT. The crease is a line in the reference; its
   gathered height is not readable.
   Reading A: a short segment, roughly 8-12% of the pant-leg length, with the
     taper-to-vertical turn concentrated there
   Reading B: the crease is a zero-height edge and knee degenerates to a
     transition ring
   Default A (follow the user's three-part spec). Either way §5.7's "exactly one
   corner, both joins C0 continuous" must hold.

4. WHETHER THE HAIR CAP ENCLOSES THE EARS. §4[14] reads the back view as showing
   an exposed skin wedge beside each ear; §7.1 reads the side views as showing the
   ears almost fully covered.
   Reading A: the ears sit outside the cap; the cap sweeps past them and the side
     views only look covered because of overlap in projection
   Reading B: the cap encloses the ears and the back-view wedges are the ear
     lobes protruding below its edge
   Default A (§4[14] is measured off back.webp, which is the head-shape authority).
   Zoom the ear region in back.webp and left.webp at >=6x before building §7.3 and
   report which reading survived.

5. HAIR THICKNESS AT THE OCCIPUT. §4[14] insets back.webp's outline by one hair
   thickness to get the skull, but thickness is only measurable at the FACE, from
   the left/right views. Hair over the back of a head is usually thicker than over
   the brow.
   Reading A: thickness is uniform — use the face measurement everywhere
   Reading B: the occiput is thicker; the skull must be inset more at the back
   Default A. This is the highest-leverage guess in the list: `head` is the last
   part built and Stage 2's hairCap and all nine spikes sit on it, so an error here
   propagates into thirteen parts. The §7.6 condition
   ("skull + hairCap = back.webp outline") is what brackets it — if §7.6 fails by
   more than measurementUncertainty and the cap itself is correct, the inset was
   wrong and Reading B is the cause. Say so rather than thickening the cap to hide
   it.
